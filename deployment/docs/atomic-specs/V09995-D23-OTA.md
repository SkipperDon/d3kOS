## 1. Why / Scope

After imaging the lab Pi and deploying to the boat, any subsequent d3kOS update currently requires a physical visit to swap the SD card. D23 eliminates this constraint for T1+ operators: the Pi polls a HostPapa command queue, downloads a signed release archive from GitHub Releases, verifies it, and self-installs — with automatic rollback if the dashboard fails to come back up.

**In scope:**
- `d3kos-ota-agent.py` — Pi-side polling + install service (BUILT S168, code gap to fix)
- `d3kos-ota-agent.service` — systemd unit (BUILT S168)
- `ota-queue.php` — HostPapa endpoint (peek / ack / result) — NOT YET BUILT
- `amboat_ota_commands` MySQL table — NOT YET BUILT
- Admin Console OTA management page — NOT YET BUILT
- Dashboard update banner integration (wires into existing Update Check agent) — NOT YET BUILT
- Settings page "Updates" section — NOT YET BUILT
- BUG-138 fix — Update Check agent reading wrong version source — NOT YET FIXED
- Guard tests (pytest) — BUILT S168, 9/9 GREEN

**Out of scope:**
- Phone app UI that triggers OTA (mobile app work, separate release)
- Release signing key management (operator generates and holds the key)
- D17 hardware-profile.json gating — OTA logs profile version in result only; it never blocks on hardware

## 2. Versioning Format (operator decision S169)

All d3kOS versions use the format: **`0.9.9.X.Y`**

- `0.9.9` — major.minor.patch (project epoch)
- `X` — feature build number
- `Y` — hotfix number (0 if no hotfix on this build)

Examples: `0.9.9.4.2` (current release), `0.9.9.5` (next), `0.9.9.5.1` (hotfix)

The OTA system must use this format everywhere — command payloads, result reports, dashboard banner, admin console, and the Update Check agent (see BUG-138).

## 3. Update Hosting (operator decision S169)

| Asset type | Host | Rationale |
|---|---|---|
| Code update tarballs | **GitHub Releases** | Already used for releases; predictable URL; easy to update/replace assets; version-labelled naturally |
| Full OS images | archive.org | Large files, permanent, already established |

The `download_url` in every command payload must point to a GitHub Release asset URL.
Format: `https://github.com/SkipperDon/d3kOS/releases/download/vX.Y.Z.A.B/d3kos-vX.Y.Z.A.B.tar.gz`

**Tarball contents — code only, never user data:**
Include: `services/`, `bin/`, `tests/`, systemd service files
Never include: `config/`, `data/`, `logs/`, `managed-documents/`

---

## 4. Queue Policy (operator decision S169)

**Latest-only per Pi.** Each Pi has at most one pending command in the queue at any time.

When the admin pushes a new version:
- If the Pi already has a pending command → replace it with the new one
- If the Pi has no pending command → insert a new one

This means a Pi that missed several releases installs only the current version directly.
It never installs intermediate versions. The tarball must always be a complete deployment, not a delta.

## 6. Pi-Side: d3kos-ota-agent.py

### 6.1 Poll interval

60 seconds. OTA is operator-initiated, not time-critical. 60 s balances responsiveness against HostPapa shared-host request budget.

### 6.2 Command schema (JSON payload from HostPapa)

```json
{
  "command_type": "ota_install",
  "command_id": 42,
  "pi_id": "device-token-string",
  "payload": {
    "version":      "0.9.9.5",
    "download_url": "https://github.com/SkipperDon/d3kOS/releases/download/v0.9.9.5/d3kos-v0.9.9.5.tar.gz",
    "sha256":       "abc123...",
    "release_notes": "Optional one-liner shown in dashboard banner"
  }
}
```

`command_type` must equal `"ota_install"` — agent ignores all other types.

### 6.3 Install flow

```
 1. Fetch pending command (GET ota-queue.php?pi_id=TOKEN&action=peek)
    → If none: sleep 60 s, repeat

 2. T1+ gate check — if T0:
    POST result "tier_insufficient"
    skip this command, sleep 60 s, repeat

 3. ACK command (POST action=ack, command_id=N) — marks "in_progress"

 4. Download archive to /tmp/d3kos-ota-{version}.tar.gz

 5. Verify SHA-256 — if mismatch:
    POST result "checksum_fail"
    delete archive, sleep 60 s, repeat

 6. Backup current deployment:
    cp -r /opt/d3kos  /opt/d3kos.ota-rollback

 7. Extract archive to /tmp/d3kos-ota-stage/

 8. Stop all d3kos-*.service units (except d3kos-ota-agent itself)

 9. rsync --archive --delete
      --exclude=config/
      --exclude=data/
      --exclude=logs/
      --exclude=managed-documents/
      /tmp/d3kos-ota-stage/  →  /opt/d3kos/

    ⚠ The four excludes are MANDATORY. They protect vessel config, boat log,
      engine history databases, and uploaded documents from being wiped.

10. systemctl daemon-reload

11. Start d3kos-*.service units

12. Health check: GET http://localhost:3000/health
    Retry up to 5 times, 5 s apart

13a. Health PASS:
     POST result "success" + version_installed + hardware_profile_version
     Delete /tmp/d3kos-ota-* and /opt/d3kos.ota-rollback

13b. Health FAIL — rollback:
     systemctl stop d3kos-*.service
     rm -rf /opt/d3kos
     mv /opt/d3kos.ota-rollback /opt/d3kos
     systemctl daemon-reload
     systemctl start d3kos-*.service
     POST result "rollback_complete" + failure detail
     Delete /tmp/d3kos-ota-*
```

### 6.4 Code gap — rsync excludes (MUST FIX before deploy)

The committed agent (`4bcf2650`) uses `rsync --archive --delete` with no excludes. Step 9 above adds four mandatory exclude flags. This fix is required before deploying to any Pi.

### 6.5 Result payload

```json
{
  "action":                   "result",
  "command_id":               42,
  "pi_id":                    "device-token-string",
  "status":                   "success",
  "version_installed":        "0.9.9.5",
  "hardware_profile_version": "2",
  "detail":                   "optional — error string on failure only"
}
```

## 7. T1+ Gate

```python
LICENSE_PATH = Path('/opt/d3kos/config/license.json')

def _check_tier() -> bool:
    try:
        data = json.loads(LICENSE_PATH.read_text())
        return int(data.get('tier', 0)) >= 1
    except Exception:
        return False  # fail closed — no OTA if license unreadable
```

## 8. HostPapa-Side: ota-queue.php

### 8.1 Actions

| action | Method | What it does |
|---|---|---|
| `peek` | GET | Returns oldest `pending` command for `pi_id`, or `{"status":"none"}` |
| `ack` | POST | Sets command status → `in_progress` (prevents double-dispatch) |
| `result` | POST | Writes result JSON, sets status → `done` or `failed` |

All requests require Ed25519 signature (same pattern as `tier_service.py` / `cloud_agent.py`).
Unsigned requests → HTTP 403. T0 devices → HTTP 403 (belt-and-suspenders with Pi-side gate).

### 8.2 Latest-only enforcement

On INSERT of a new command for a `pi_id`:
```sql
UPDATE amboat_ota_commands
   SET status = 'superseded'
 WHERE pi_id = ? AND status = 'pending';
-- then INSERT the new command
```
This ensures only one pending command per Pi at all times.

### 8.3 MySQL table

```sql
CREATE TABLE IF NOT EXISTS amboat_ota_commands (
  id                       INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  pi_id                    VARCHAR(64)   NOT NULL,
  command_type             VARCHAR(32)   NOT NULL DEFAULT 'ota_install',
  payload                  JSON          NOT NULL,
  status                   ENUM('pending','in_progress','done','failed','superseded')
                                         NOT NULL DEFAULT 'pending',
  result_status            VARCHAR(32)   NULL,
  version_installed        VARCHAR(20)   NULL,
  hardware_profile_version VARCHAR(10)   NULL,
  install_timestamp        DATETIME      NULL,
  detail                   TEXT          NULL,
  created_at               DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at               DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_pi_status  (pi_id, status),
  INDEX idx_created    (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Key additions vs. v1.0 spec: `result_status`, `version_installed`, `hardware_profile_version`,
`install_timestamp`, `detail` as proper columns (not buried in JSON) — required for Admin Console display.

## 9. Admin Console OTA Management Page

**Purpose:** Operator interface to push updates and track Pi install status.

**Functions:**

| Function | Detail |
|---|---|
| Push update | Enter: version (`0.9.9.X.Y` format), GitHub Release URL, SHA-256. Select: target Pi(s) or "All T1+ devices". Confirm before queuing. |
| Per-Pi status | Table: Pi ID / nickname, current installed version, pending version (if any), install status, install timestamp |
| Cancel queued update | Mark pending command as `superseded` before Pi polls |
| Install history | Last N results per Pi (status, version, timestamp, detail on failure) |

**Version validation:** Admin Console must reject any version string that does not match `\d+\.\d+\.\d+\.\d+(\.\d+)?`. Rejects `v1.0.3` or other malformed strings before they reach the queue.

## 10. Dashboard Integration

### 10.1 Update banner (wires into existing Update Check agent)

The Update Check agent (`AA-update`) already detects available updates and shows a banner.
D23 wires the install action into that existing banner.

Banner when update available:
```
┌─────────────────────────────────────────────────────┐
│  d3kOS 0.9.9.5 available                           │
│  [Dismiss]                    [Update d3kOS]       │
└─────────────────────────────────────────────────────┘
```

- **[Dismiss]** — hides banner until next version; does NOT cancel the queued command
- **[Update d3kOS]** — calls Pi-local endpoint that triggers the OTA agent to act immediately (skip the 60 s wait); shows progress indicator while install runs

AODA: 18px minimum, 48×48px touch targets, sufficient contrast.

### 10.2 Settings → Updates section

Location: existing Settings page, new "Updates" section.

Displays:
- Current version: `0.9.9.4.2`
- Available version: `0.9.9.5` (or "Up to date")
- Last checked: `2026-09-17 14:18 UTC`
- [Check Now] button — triggers immediate poll
- [Install Now] button — visible only when update is queued; same action as banner [Update d3kOS]

### 10.3 BUG-138 — Update Check agent version mismatch (MUST FIX)

The Update Check agent currently reports `v1.0.3` — this is not a d3kOS version.
It is reading the wrong source (likely a `package.json` Node version).

**Required fix:** agent must read from `license.json → version` field or `version.txt`.
Format must be `0.9.9.X.Y`. Fix this before dashboard banner integration — the banner
will display whatever the agent reports.

## 11. Systemd Unit

```ini
[Unit]
Description=d3kOS OTA Update Agent (D23)
After=network-online.target signalk.service d3kos-dashboard.service
Wants=network-online.target

[Service]
Type=simple
User=d3kos
Group=d3kos
WorkingDirectory=/opt/d3kos/services/ota
ExecStart=/usr/bin/python3 /opt/d3kos/services/ota/d3kos-ota-agent.py
Restart=on-failure
RestartSec=30
StandardOutput=journal
StandardError=journal
SyslogIdentifier=d3kos-ota-agent

[Install]
WantedBy=multi-user.target
```

`Restart=on-failure` (not `always`) — avoids BUG-105 restart-loop pattern.
`RestartSec=30` — crashed agent must not hammer HostPapa.

## 15. Design Decisions (S169 2026-09-17)

| Decision | Choice | Rationale |
|---|---|---|
| Update host | GitHub Releases | Already used; predictable URL; easy asset replacement |
| OS image host | archive.org | Unchanged — large permanent files |
| Version format | `0.9.9.X.Y` | Existing project scheme; enforced by Admin Console validation |
| Queue policy | Latest-only per Pi | Simpler; avoids stale intermediate versions; full tarball always |
| Data protection | rsync excludes `config/` `data/` `logs/` `managed-documents/` | These are user data — never overwritten by a code update |
| Admin interface | Admin Console OTA page | Operator-facing; keeps atymboat.com admin in one place |
| Banner | Wires into existing Update Check agent | Reuses existing detection; no new polling service |
| T0 treatment | Blocked — no OTA | T0 requires physical access; OTA is a T1+ feature |
