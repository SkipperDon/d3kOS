## Cross-cutting (applies to every spec in this batch)

### Q0.1 — Which tree do I edit, the repo or the Pi?
**A:** The repo, and **only** `deployment/v0.9.9.4/`. That tree was seeded from the running lab Pi
on 2026-07-27 and is now the single canonical source. Its layout mirrors full Pi paths, so
`deployment/v0.9.9.4/opt/d3kos/services/dashboard/app.py` → `/opt/d3kos/services/dashboard/app.py`.

### Q0.2 — May I deploy my change to the Pi to test it?
**A:** **No.** Deployment is a separate High-risk step requiring explicit operator authorisation in
the session it happens. There is also a standing hold: no Pi changes until the operator's SD-card
backup is confirmed complete. Repo edit + local test only.

### Q0.3 — `deployment/v0.9.4/pi_source/` and `deployment/d3kOS/dashboard/` still exist. Do I touch them?
**A:** **Never edit them.** Both are SUPERSEDED. `pi_source` is the v0.9.9.2 release tree and is your
**read-only reference** for BUG-36 and BUG-37 — copy *from* it, never write *to* it.
`d3kOS/dashboard` is the wrong lineage that caused BUG-36; ignore it entirely.

### Q0.4 — After my edit, is `MANIFEST.md5` now wrong?
**A:** Yes, and that is expected. `MANIFEST.md5` records what is *deployed on the Pi*, not what is in
the repo. Do **not** regenerate it — it is regenerated by Tier 1 at deploy time. Leave it alone.
`tools/check-drift.sh` will correctly report drift for your file until the deploy happens.

### Q0.5 — How do I run the dashboard to test?
**A:** Flask app, `deployment/v0.9.9.4/opt/d3kos/services/dashboard/app.py`, serves on port 3000 on
the Pi. Locally it will not fully run (it reads `/opt/d3kos/config/*` and talks to Signal K on
:8099 and ai-bridge on :3002, none of which exist off-Pi). **Therefore:** prefer static tests —
Python `ast`/import checks and DOM/string assertions — over live-server Playwright tests for this
batch. Where a spec asks for a live test, it says so explicitly and provides the harness.

## BUG-36 — restore the `_d3kEngData` cache

### Q36.1 — The v0.9.9.2 source uses `propulsion.0.*` paths, but BUG-29 says Signal K actually publishes `propulsion.port.*`. Which do I use?
**Why it blocks:** copying verbatim reinstates paths that are known to deliver no data.
**A:** Use **`propulsion.0.*` — copy verbatim.** Do not fix the paths in this spec. Reasons:
(1) BUG-29 is a separate defect with its own spec and its own blast radius of six files; mixing the
two makes both unreviewable; (2) the cache must be restored *identically* to the v0.9.9.2 original so
the diff is provably a pure restoration; (3) BUG-29's fix changes the path in one place and the cache
then works automatically. **Restoring a cache on a dead path is still correct** — it fixes the
structural loss, and BUG-29 turns the data on.

### Q36.2 — `fuel_pct` stores the raw fraction `v` (0–1), not the percentage. Is that a bug to fix?
**A:** **Not a bug — copy it verbatim.** `_diagReadingsSummary()` does
`Math.round(eng.fuel_pct * 100)`, so it expects the fraction. Storing a percentage here would
produce a 100× error. Leave the local `const pct` line exactly as it is.

### Q36.3 — Where exactly does the declaration line go?
**A:** Immediately before the `/* ── CELL STATE ── */` comment block, preceded by its own comment,
mirroring `pi_source/instruments.js` lines 25–26 exactly:
```js
/* ── LIVE ENGINE DATA CACHE (populated by SK handlers, read by openDiag) ── */
window._d3kEngData = { coolant_c:null, oil_psi:null, rpm:null, bat_v:null, fuel_pct:null };
```

### Q36.4 — The canonical file's handlers differ from `pi_source` (S105 added `_lastSogKts`). Can I just copy the whole file over?
**Why it blocks:** copying the whole file would delete the S105 COG fix and re-create BUG-15.
**A:** **No — absolutely not.** Add only the six lines (one declaration + five cache assignments)
into the *existing* canonical file. Do not replace handler bodies, do not replace the file. The
S105 `_lastSogKts` code at canonical lines 121, 126 and 135 must survive untouched — verifying that
is part of Done.

## BUG-35 — OTA must preserve all four `version.txt` fields

### Q35.1 — Where do Release Date, Status and Build come from during an OTA?
**Why it blocks:** determines whether the fix reads the manifest or preserves existing values.
**A:** The OTA release manifest is a dict (`release`), and the only key confirmed to exist is
`version` (`latest_ver = release.get('version', 'unknown')`, line 227). **I have not confirmed that
the manifest carries a release date, status or build.** Therefore the binding contract is
**read-modify-write**: parse the existing four fields, replace `d3kOS Version` and `Build` from
`latest_ver`, and **preserve `Release Date` and `Status` unchanged**. Additionally, *if* the manifest
happens to contain `release_date` or `status` keys, use them — guarded with `.get()` so an absent key
is not an error. That is correct whether or not the keys exist.

### Q35.2 — Three copies of `ota_upgrade.py` exist and two of them differ. Which do I edit?
**A:** Edit **both** copies present in the canonical tree:
`opt/d3kos/services/ota_upgrade.py` and `opt/d3kos/services/cloud-agent/ota_upgrade.py`.
The **cloud-agent copy is the live one** (`d3kos-cloud-agent.service` sets
`WorkingDirectory=/opt/d3kos/services/cloud-agent`). The two files are **not** identical
(md5 `7043f1d7…` vs `6105de65…`), so apply the fix to each in place — do **not** copy one over the
other, and do not attempt to reconcile their other differences. Reconciliation is a separate task.

### Q35.3 — What if `version.txt` is missing or malformed when the OTA runs?
**A:** Write all four fields with the new version and `Release Date: unknown`, `Status: unknown`.
Never crash the OTA — the existing `try/except` that appends to `errors` stays as the outer guard.

> **Correction (Tier 1, same session):** an earlier draft of this answer said today's date was "not
> available deterministically." That was **wrong** — `ota_upgrade.py` imports `datetime` at line 30.
> The instruction to write `unknown` still stands, but for a different and better reason: the
> install date is **not** the release's date, so writing it into `Release Date` would record a value
> that is simply untrue. That is the same class of wrong-metadata defect BUG-35 exists to fix.
> **Do not invent a date.** Preserve the existing value, or take it from the manifest, or write
> `unknown`.

## BUG-39 — first-boot identity regeneration

### Q39.1 — ⛔ **NEEDS OPERATOR** — Is `installation_id` (currently `3861513b314c5ee7`, tier T3) per-device or per-owner?
**Why it blocks:** if per-device, the clone must get a new one and be re-licensed. If per-owner, it
must be **preserved** or the boat Pi loses its T3 entitlement. Guessing either way risks either a
licence collision or an unlicensed boat.
**Status:** unanswered. The script must leave `license.json` **untouched** until this is answered.

### Q39.2 — ⛔ **NEEDS OPERATOR** — Does regenerating `device_token` break the existing PWA pairing and the device's history on atmyboat.com?
**Why it blocks:** `device_token` is the identity key in `amboat_devices`. A new token likely appears
as a brand-new device, orphaning existing telemetry, tickets and PDF reports.
**Status:** unanswered. Needs a decision on whether the **lab** or the **boat** keeps the existing
token, and whether the other is re-paired from scratch.

### Q39.3 — Where is the Signal K vessel UUID stored, and is changing it safe?
**Why it blocks:** the UUID is duplicated by any clone.
**A (partial):** the value is served at
`http://localhost:8099/signalk/v1/api/vessels/self/uuid` and is
`urn:mrn:signalk:uuid:e1592142-4955-4b4d-a085-40fa674e0e13`. **I have not confirmed which file on
disk holds it** — candidates are `~/.signalk/settings.json`, `~/.signalk/defaults.json` and
`~/.signalk/baseDeltas.json`. **Tier 3 must not guess.** The spec therefore requires the script to
*locate* the file at run time and fail loudly if it cannot, rather than hardcoding a path.

### Q39.4 — How is the script triggered on first boot, and how does it avoid running twice?
**A:** A systemd oneshot unit ordered before the d3kOS services, guarded by a sentinel file. Contract:
if `/opt/d3kos/config/.identity-regenerated` exists, exit 0 immediately and do nothing. Otherwise
regenerate, then create the sentinel. The **cloning process must delete the sentinel** on the clone —
that deletion is an operator/clone-procedure step, not something the script can do to itself.

### Q39.5 — Should the script regenerate filesystem UUIDs too?
**A:** **No — out of scope.** `tune2fs` is not installed on the Pi (`e2fsck` and `parted` are also
absent), and changing a mounted root filesystem's UUID is unsafe. The operator is instead ticking
**"New Partition UUIDs"** in the Pi's SD Card Copier, which handles it at clone time. Note this in
the script's header comment so nobody adds it later.
